A knowledge base searches one or more data sources together. Agents answer from knowledge bases, and API keys can search them directly. Editors, admins and owners manage them under **Knowledge bases** in the team's sidebar.

## Creating one

1. **Knowledge bases → New knowledge base.** Give it a name, an optional description, an **embedding profile** and **Results per query (top-k)**, a whole number from 1 to 50. You can't change the profile yourself (see [Changing the embedding profile](#changing-the-embedding-profile)), and only sources that use it can be attached.
2. **Attach source** on the **Sources** tab. You can attach your team's own sources and platform-shared sources, as long as each is classified within your team's approved level.
3. Wait until the sources have ready documents, then try a search.

A knowledge base is as sensitive as its most sensitive source. That level decides which chat models its agents may use and which audiences they may have.

## Try it

The **Try it** tab runs the same hybrid search agents use (vector and keyword together), without a chat model. Type a question and see the passages that come back, ranked, with their document, heading path and score.

<Screenshot slot="kb-try-it" />

Under **Filters and options** you can narrow a search, the same filters agents can pin:

- **Sources**: only these data sources.
- **Document kinds**: PDF, Word, PowerPoint, web page, Markdown and so on.
- **Tags**: documents with any of these tags.
- **URL prefixes**: web pages whose address starts with one of these.
- **Updated on or after** and **Updated before**.
- **Results per query (top-k)**: how many passages to return.
- **Judge with SystemOne** (when the platform has a SystemOne model): shows each passage's relevance scores and whether passage judging would keep it.
- **Rerank** (when the platform has a [rerank model](/docs/administration/reranking), on by default): the passages that best answer the question come first, as agents get them. Each passage shows its **Rerank** score beside the usual score, and the result says how the search was reranked ("Reranked the best 40 passages in 452 ms"). Turn it off to compare with the usual order; switching it searches again.

<Screenshot slot="kb-try-it-rerank" />

Use **Try it** to check a knowledge base before you point an agent at it, and whenever answers cite the wrong things. An evaluation result's **Try this search** opens this tab with the question filled in.

## Retrieval settings

On **Settings → Retrieval**:

- **Passages per search**: how many passages a search returns, between 1 and 50. Agents use this number unless they override it (see [Agents](/docs/using/editors/agents#knowledge)).
- **Vector weight** and **Keyword weight** (each 0–1): how the vector search and the keyword search are fused. **Use the default** takes the embedding profile's weights if it sets them, otherwise the platform's (vector 1, keyword 0.1).

The default suits most content. A knowledge base full of codes, names and policy numbers may do better with a higher keyword weight. Some strong embedding models do better with keyword fusion turned down to 0 or close to it; your platform admin may already have set that on the profile. Check changes on **Try it**, or better, with an [evaluation set](/docs/using/editors/evaluations).

## How search works

For each question, Grounded:

1. Rewrites a follow-up that depends on the conversation into a question that stands alone (agents only, if turned on). A question that already stands alone is searched as it is.
2. Embeds the question with the knowledge base's profile.
3. Runs a vector search and a keyword (Postgres full-text) search at the same time, both limited to the knowledge base's sources and any filters.
4. Fuses the two rankings with the weights above.
5. Reranks the best of them, when the platform has a [rerank model](/docs/administration/reranking) and reranking is on, and returns the top passages.
6. For agents only, when the embedding profile uses **parent sections** (v0.7.0): passages from the same section count as one source, and the model is given the whole section around each match, up to the profile's section size and within the answer's source token budget. A section that doesn't fit, or has changed, is replaced by the matched passage. Ranking still uses the passages.

**Try it**, the retrieval API and the MCP `search` tool return the passages themselves, ranked as above, never sections.

Small knowledge bases are searched exactly; very large ones use an approximate vector index. An agent that uses several knowledge bases searches each with its own profile and merges the results.

## Changing the embedding profile

A knowledge base's profile can't be edited, but a platform admin can **migrate** it to a new profile in the background, for example to adopt a better embedding model. Search keeps working throughout, the switch happens in one step, and it can be switched back for a grace period. While it runs, the knowledge base's page says "Moving to the embedding profile *name*" with a **Documents re-embedded** meter. See [Embedding profiles](/docs/administration/embedding-profiles).

Platform admins who are also members of the team see **Change embedding profile…** and **Preview new settings…** in the knowledge base's "…" menu. Both open the admin portal.

### When a platform admin previews new settings

Since v0.5.0 a platform admin can try new index settings on a knowledge base before anything changes: a second index is built beside the current one, and the knowledge base's evaluation sets are run on both. In v0.7.0 a preview can change the passage size and overlap, the embedding model, the prefixes, the chunker (versions 1 to 4), parent sections, near-duplicate repeated blocks and contextual chunks.

The knowledge base's page then says "A platform admin is trying new index settings on this knowledge base":

- **While it builds:** "The new index is being built. Search and agents keep using *profile*, and nothing changes for you unless the platform admin switches.", with a **Documents embedded** meter.
- **When it's ready:** "Your evaluation sets were run on both; what changed is below." For each evaluation set it gives recall and MRR now and with the new index, and how many questions got better, worse or stayed the same. **Questions that changed** lists each one with **Question**, **Current index**, **New index** (the rank its expected document came back at, or "not found") and **Change** (**Better** or **Worse**).

<Screenshot slot="kb-index-preview-ready" />

Search and agents keep using the current index until the platform admin switches; they can also discard the preview. After a switch, the page says "Now on the embedding profile *name*", and the admin can switch back during the grace period.

- Only the knowledge base's own evaluation sets are compared, retrieval only. Without evaluation sets there is nothing to compare. See [Evaluations](/docs/using/editors/evaluations#index-previews).
- A preview that changes only parent sections shows no difference, because the comparison scores passages, not sections.
- The comparison runs count towards the team's query usage.

## Other tabs

- **Overview**: **Data sources**, **Documents ready**, **Passages** and **Used by agents**, with the profile, sources and passages per search in the header.
- **Evaluations**: test sets for its search. See [Evaluations](/docs/using/editors/evaluations).
- **Settings**: name, description, retrieval, and delete. Deleting a knowledge base keeps its data sources; published agents that use it must drop it first.

## Searching through the API

`POST /v1/teams/{team}/kbs/{kbId}/retrieve` runs the same search for a signed-in session or an API key with the `query` scope. Each search counts against the team's query limits. Since v0.6.3 a `topK` outside 1 to 50 is refused (`400 invalid_topk`) instead of being adjusted; leave it out to use the knowledge base's setting. Whether team API keys may call it directly for a given classification level is a platform setting. See [the API reference](/docs/api/reference/kbs/retrieve).
