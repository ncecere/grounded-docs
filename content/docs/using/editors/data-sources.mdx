A data source holds documents. Grounded parses each document, splits it into passages and indexes them, so knowledge bases can search them. Team editors, admins and owners create and manage sources under **Data sources** in the team's sidebar.

When you create a source you choose:

- **Type**: **Upload files** or **Website**. It can't change later.
- **Embedding profile**: how documents are cut into passages and how passages are embedded. A knowledge base can only combine sources that use the same profile. You can't change it yourself: a platform admin can move it to another profile (a profile migration), or try new settings with an [index preview](/docs/using/editors/knowledge-bases#when-a-platform-admin-previews-new-settings).
- **Name**, **Description** (optional) and **Classification**. These can change later; the classification is [covered below](#classification).

## Uploading files

An upload source accepts PDF, Word (DOCX), PowerPoint (PPTX), HTML, Markdown and text files. With OCR on, it also accepts PNG, JPEG and TIFF images (see [OCR](#scanned-documents-and-ocr)).

- Choose **Upload files** on the source, or drop files on it. Each file becomes a document.
- The default size limit is 100 MB per file; your platform may set another.
- Uploading a file whose content is already in the source changes nothing. Uploading a new version of a file replaces the document.
- **Tags for these files**, in the **Upload files** dialog, are added to every file of that upload, so agents and searches can filter on them. A replaced file keeps its tags unless you set some. **Edit tags** in a document's row changes one document's tags.
- Since v0.6.3 a file whose name contains control characters or invisible formatting characters (such as zero-width or text-direction marks) is refused rather than renamed, and a file over the size limit is refused with a message that states the limit.
- Files can also be uploaded through the API, with an API key that has the `ingest` scope.

Grounded parses these formats itself. PDFs are read by PDFium (Chrome's PDF engine) running sandboxed in WebAssembly; headings are inferred and repeating page headers and footers removed. Word files keep their headings, lists and tables; PowerPoint files become one page per slide, with speaker notes. An install may also run Apache Tika as a fallback parser.

- **Tables with merged cells** (v0.7.0): a cell that spans rows in HTML (`rowspan`), or spans or merges cells in Word (`gridSpan`, `vMerge`), now keeps the cells after it under their own column headers. This changes the parsed text of such tables the next time a document is processed.
- **Images in HTML** without alt text are dropped (v0.6.3); images with alt text are unchanged.
- **Tables in PDFs** are read as paragraphs: the PDF parser reads lines, not table structure.

How a document is then cut into passages depends on the source's embedding profile, which a platform admin sets up. Its **chunker** may keep tables whole, repeating the caption and header row in each piece of a long table (version 3), and may also never run a passage across a heading or across a bold label above a list (version 4). A profile may also use **parent sections**, which give agents the section around each matched passage. See [Embedding profiles](/docs/administration/embedding-profiles#chunkers).

## Crawling a website

A website source fetches public web pages with Grounded's own crawler. Choose what to index:

| Mode | What it does |
|---|---|
| **Single page** | Fetches one URL. |
| **List of pages** | Fetches up to 1,000 URLs you list, one per line. Links aren't followed. |
| **Crawl a site** | Starts from up to 20 start URLs and follows links on the same host, within a depth and a page limit. |

For a crawl you can set:

- **Maximum depth**: link hops from a start page, 0 to 10.
- **Maximum pages**: the crawl stops there. The platform sets the ceiling.
- **Path prefixes**: only follow paths that start with these, such as `/admissions/`.
- **Exclude patterns**: skip matching paths, such as `/calendar/**`. `*` matches within a path segment, `**` across segments.
- **Include subdomains** and **Use sitemaps** (also start from the pages listed in robots.txt and sitemap.xml).

**Preview pages** shows the URLs a crawl would start with, without storing anything. Use it to check the scope before you create the source. If the start page can't be read, the preview says what the site answered, for example "That page returned 404 (not found). Check the address." (v0.4.2).

The crawler always respects robots.txt, spaces its requests to each site, and doesn't run JavaScript: pages that only render their content in the browser come back empty. It fetches public sites only; sites behind a sign-in aren't supported. PDF, Word (DOCX), PowerPoint (PPTX) and Markdown files it finds are parsed like uploads. Since v0.6.3, links to files it can't read (archives, installers, disk images, pictures, audio, video, fonts, and office formats such as `.doc`, `.xls`, `.xlsx`, `.ppt` and OpenDocument files) are skipped without being fetched.

### Keeping a website current

- **Sync schedule**: manual, daily or weekly. A scheduled sync fetches the pages again and picks up changes. **Sync now** runs one at any time.
- Pages that are missing from a completed full crawl are removed from the source, and from search at once.
- A single page can be fetched again from its row on the **Pages** tab.
- The **Crawls** tab shows the 20 most recent crawls with their results.
- A sync that **fetched nothing** says why (since v0.6.1). It still finishes as **Completed**, but the **Crawls** tab shows a line under the status that starts "Nothing was fetched:" and gives the cause that skipped most pages: "the site's robots.txt doesn't allow it", "the site couldn't be reached (its robots.txt could not be read)", "the address isn't a public website (only public sites on ports 80 and 443 can be crawled)", "the host isn't on the crawl allowlist", "the pages aren't a kind Grounded can read", or, if none of those fits, "every page was skipped". A robots.txt that can't be reached is its own cause: before, it was reported like a robots.txt that forbids crawling. Pages that failed count as fetched, so a sync with failures has no such line; its failures are in the counts.

### Crawl domains

Websites can only be crawled if their host is on the platform's **crawl allowlist**. If a site you need isn't on it, request it:

1. Open **Data sources → Crawl domains** (or follow the prompt when a new website source is refused).
2. Request the domain, with a reason.
3. A platform admin approves or declines it. You get a notification with the decision, and the tab shows each request's status.

Approved domains apply to your team only. Private, loopback and link-local addresses are always refused, whatever the allowlist says, so internal sites can't be crawled. Since v0.6.1, creating a source at such an address (`127.0.0.1`, `10.x`, `169.254.169.254`, `::1`) is refused as `400 blocked_address` with a message that says the crawler never fetches it and a domain request can't change that. Before, it answered as if the host were only missing from the allowlist and invited a domain request that could never be approved.

## Repeated blocks

Websites repeat text on many pages: navigation, footers, "related content" cards. If those blocks were indexed, answers would cite them instead of real content. Grounded finds blocks that appear on many of a source's pages and leaves them out of search, keeping one copy so their information is still indexed once.

It's controlled on the source's **Overview**, in the **Repeated blocks** card. Editors, admins and owners see its switches; everyone in the team sees what was removed.

- **Remove repeated blocks** is on by default for website sources and off for uploads.
- The card shows how many repeated blocks were removed from how many pages, and the rule in force. **Show the most repeated blocks** lists them.
- Changing the setting re-checks every page from its stored text in the background. Nothing is fetched again.

### Near-duplicate blocks

Removal matches blocks by their exact text, so a menu with a different item highlighted on each page, or a footer with a different date, used to be kept on every page. Since v0.7.0, **Also remove near-duplicate blocks** (off by default, under **Remove repeated blocks**) treats blocks of eight words or more that differ a little from page to page as one repeated block. Blocks that only share some words are kept. The switch is disabled until **Remove repeated blocks** is on.

- In **Show the most repeated blocks**, a group of near-duplicates is listed once, with how many pages have it and how many variants it has ("34 pages, 3 variants").
- Turning it on or off re-checks the pages from their stored text in the background. Nothing is fetched again, and only pages whose removed blocks change are cut into passages again.
- It changes what the source's knowledge bases search as soon as the re-check finishes. A platform admin can try it first with [Preview new settings](/docs/administration/embedding-profiles#near-duplicate-repeated-blocks), which builds a second index beside the live one and compares them; switching to that index turns the setting on for its sources.

## Contextual chunks

Since v0.7.0 a platform admin can opt a source in to **contextual chunks**: a chat model writes a short description of where each section sits in its document, and that text is added only to what is embedded. Passages, keyword search, citations and the source viewer don't change. It's off by default, for the install and for each source, and only platform admins can configure it.

Everyone in the team sees a read-only **Contextual chunks** card on each source's **Overview**:

- "Off for this source. No contextual model work is authorized.", or "Opted in with *model*" once a platform admin has set it up.
- "Contextual chunks are switched off for this installation." while the install's switch is off.
- **Model attempts**, **Unknown-usage attempts** and **Cached contexts**. No spend is shown.
- "Only platform admins can configure this opt-in and its spending limits. Ask one to estimate and preview it first."

A platform admin turns it on for a knowledge base through an index preview, and nothing changes for your agents until they switch to it. The model calls are recorded as chat tokens of the chosen model, so they count towards your team's daily chat tokens and monthly budget ([Usage and spend](/docs/using/owners/usage-and-spend#contextual-chunks)); when a limit or the budget is reached, documents wait. See [Contextual chunks](/docs/administration/contextual-chunks) for how platform admins set it up.

## Scanned documents and OCR

Scanned PDF pages and images have no text layer. If your platform has turned OCR on, Grounded reads them:

- Only pages without a text layer are read with OCR. Their text goes under the page's marker, so citations still name the page.
- PNG and JPEG uploads become one-page documents. A TIFF gets a page for each of its pages (since v0.4.1; before, only the first page was read), each read with OCR under its own page marker, within the OCR limits below. A page that can't be read is a warning.
- A document's page says which pages were read with OCR, for example "Pages 3–7 were read with OCR (Tesseract)".
- Each source has its own switch, **Settings → Read scanned pages with OCR**, on by default. Turn it off where scans are noise. With it off, scanned pages are skipped and images can't be uploaded to the source.

<Screenshot slot="source-document-ocr" />

Documents skipped as scanned before OCR was on show as **Needs OCR**. On the source's **Documents** tab, filter **Needs OCR**, then **Retry all that need OCR**, or open one and choose **Retry with OCR**. The buttons are disabled while OCR is off for the source or the platform, and the reason is shown at the top of the document's page, for example "OCR is off for this source. Turn it on in the Settings tab first; until then, scanned pages can't be read."

**Partly scanned PDFs** (since v0.4.1): a PDF with only some pages lacking text, processed while OCR was off, is indexed with its typed pages and shows **Ready**, with a warning that names the pages it couldn't read ("Page 2 has no text layer (it may be a scan) and wasn't read, because OCR is off for this document. Once OCR is on, retry it to read that page."). It also needs OCR: the **Needs OCR** filter finds it, and once OCR is on, **Retry all that need OCR** or its own **Retry with OCR** reads it again, sending only the pages without text to OCR. It keeps its passages until then. PDFs processed before v0.4.1 have only the old warning and aren't in the filter: to read their scanned pages, delete them and upload them again (uploading the same file over one changes nothing).

OCR has limits: pages per document (200 by default) and **OCR pages per day** for the team (1,000 by default). A document that would pass the daily limit waits with "Waiting for the team's daily OCR page limit" and continues the next day (UTC), or as soon as the limit is raised.

## Document states

<Screenshot slot="source-documents-ocr" />

A document moves through pending, fetching, parsing, chunking and embedding to **ready**. Others end as **failed** (with the error; you can retry), **skipped** (empty, or needs OCR) or **deleted**. A document can also **wait**: for the team's daily OCR or crawl page limit, for its monthly budget when the platform enforces budgets, while the platform is in maintenance mode, or, for a source opted in to [contextual chunks](#contextual-chunks), for that source's call, token or price limits or the team's daily chat tokens.

Select documents in the table to retry or delete several at once. Since v0.4.2 the selection follows what the table shows: a filter, a search or another page clears the rows it hides, so the bar, the footer and the **Delete** dialog count the same rows and Delete removes exactly the ones it names. A disabled **Retry** says why beside it.

To find failed documents, pages not processed in a long time, links the last crawl saw fail and the same file in two sources across all your sources at once, ask for a [content health report](/docs/using/editors/content-health).

## Classification

A source's classification says how sensitive its data is. It limits which models may embed it and which audiences its agents may have. A knowledge base takes the level of its most sensitive source, and an agent the level of its most sensitive knowledge base.

- **Raising** a classification is allowed for editors. It's refused, with the affected knowledge bases and agents named, if it would break a rule for any of them (for example an agent shared more widely than the new level allows). Nothing is ever unpublished silently.
- **Lowering** it needs a team admin or owner and a written reason. The team's owners are notified, and the change is audited.
- A source can't be classified above the team's approved level.

## Other actions

- **Pause source**: it accepts no uploads, and documents waiting to be processed wait. Documents already indexed stay searchable. Resume it to continue.
- **Delete source**: its documents leave search at once. Their stored files are removed later, according to the platform's retention settings. A source that knowledge bases still search can't be deleted: since v0.4.2 the dialog names them, with links to their Sources tab, and offers no Delete until you detach it.
- Deleting a document works the same way.

Your team's limits cap storage, documents, sources, crawl pages per day and concurrent crawls. A crawl that reaches the daily page limit waits until the next day (UTC) or until the limit is raised; it doesn't fail. Owners and admins see the limits under [Usage and spend](/docs/using/owners/usage-and-spend).

## Shared sources

Platform admins can create **shared sources** that any team can attach to its knowledge bases. They appear when you attach a source to a knowledge base. You can't change a shared source, and it doesn't count against your team's limits.
