title: API keys

API keys let programs use the team's agents and knowledge bases without a browser: the [OpenAI-compatible endpoint](/docs/api/openai-compatible), the agent chat API, knowledge base search, uploads, and [AI tools over MCP](/docs/using/mcp). Create them under **Team settings → API keys**. Admins and owners see every key of the team; others see their own.

## Kinds

| | Personal key | Service key |
|---|---|---|
| Belongs to | You, in this team | The team |
| Who creates it | Any member | Admins and owners |
| Scopes | Depend on your role (below) | Any |
| When you leave the team | Revoked automatically | Keeps working |
| Conversations | Stored for you, like your chats | Stateless: send earlier turns with each request |

A service key has a **responsible contact**, a team member to ask about it, shown in the key list. An admin can change the contact later.

## Scopes and restrictions

| Scope | Allows | Who can grant it on a personal key |
|---|---|---|
| **Query** | Chat with agents and search knowledge bases | Everyone |
| **Ingest** | Upload documents to a data source, start and cancel a crawl, preview a site map, and read sources, documents and agents | Editors, admins, owners |
| **Manage** | Today the same calls as Ingest | Admins, owners |
| **MCP** | Search knowledge bases and ask agents from AI tools, over the [MCP server](/docs/using/mcp). Nothing on the REST API | Everyone |

Neither Ingest nor Manage can create, change or delete data sources, knowledge bases, agents or members, or publish an agent: those need a person signed in to the app (a key gets `401` there).

A key can also be **restricted** to some knowledge bases and some agents. Leave them unchecked to allow every knowledge base, or every agent, of the team.

- A **knowledge-base** restriction limits the knowledge bases the key can search, the data sources it can reach (only the sources the chosen knowledge bases use) and those sources' documents. Any other source, and its documents, don't exist for that key. A key restricted to knowledge bases, and to no agents, also doesn't list or open an agent whose draft or published configuration uses any other knowledge base.
- An **agent** restriction limits which agents the key may use and see, and (since v0.6.1) the knowledge bases it reaches: only those the chosen agents' **published** versions answer from. The key follows them: publish a different version of an agent and the key's reach changes with it. An agent that isn't published, or answers from no knowledge base, adds none. Its sources and documents follow the same rule.
- With **both** restrictions, the key reaches only the knowledge bases that both allow: those the chosen agents answer from, and among them only the ones you ticked.

<Callout type="warn" title="Keys restricted to agents reach less since v0.6.1">
  Before v0.6.1 an agent restriction did not limit knowledge bases, so such a key could search every knowledge base of the team. It now reaches only what its agents' published versions answer from, and a restriction to knowledge bases alone now hides agents that use others. If a program stopped finding something after the upgrade, look at the key's restrictions on its page: add the agent that answers from the knowledge base, or tick the knowledge base too.
</Callout>

A key can have an **expiry date**; it stops working at the end of that day.

A personal key acts as you and never does more than your role in the team allows now: if you are made a plain member, its Ingest scope stops working at once (it does not have to be revoked). If you leave the team, it is revoked.

A key with only the Query scope, or one whose owner is a plain member, sees the team's agents as a member does: each agent's profile and published version, not its draft (see [Authentication](/docs/api/authentication#api-keys)).

Keys always belong to one team, and can never administer the platform.

The **MCP** scope works only while a platform admin has turned the MCP server on; the form says when it's off. A key with only the MCP scope can't call the REST API, and a key for AI tools doesn't need Query. Over MCP a key reaches exactly what it could reach as a query key: its team, and only the knowledge bases and agents it's restricted to.

## Creating one

1. **Team settings → API keys → New API key.** (Since v0.4.4 your own personal keys, across all your teams, are also listed under **API keys** in the account menu, each linking to its page here, with a **Create a key** link per team.)
2. Name it after what will use it ("Course site search"), pick personal or service, the scopes, any restrictions, and optionally an expiry date (a calendar; choose the day again to clear it).
3. Copy the secret. **It's shown once**, right after creation; Grounded stores only a keyed hash of it. The dialog also shows an example request, and for a key with the MCP scope the MCP server's address.

Keys look like `rag_<id>_<secret>`. Send them as a bearer token:

```sh
curl -H "Authorization: Bearer $GROUNDED_API_KEY" https://grounded.example.org/v1/models
```

## Revoking

**Revoke…** stops the key at once; programs using it get 401. It can't be undone. Revoked keys stay visible from the audit log, read-only, so the history keeps making sense.

Each key's page shows when it was created and last used. Revoke keys nobody uses. If a key may have leaked, revoke it and create a new one.

## Connected apps

When the platform allows [OAuth sign-in for AI tools](/docs/using/mcp#oauth-sign-in-experimental) (experimental), this page also lists **your own** connected apps: the AI tools you signed in to with your Grounded account, with **Disconnect…**. They aren't team keys, and only you (and platform admins) see them.

<Callout title="When the platform rotates its pepper">
  Platform operators occasionally rotate the secret used to hash API keys. Keys keep working if they're used during the grace period the operators set. A key that isn't used in that time stops working, and you'll need to create a new one. See [Security](/docs/self-hosting/security#rotating-keys).
</Callout>
